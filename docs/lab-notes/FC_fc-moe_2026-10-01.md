## 1. The routing prologue gained ~5 µs per call between the G2 build and production (bit-exact candidate)

Median duration of `fusedBuildExpertMapsSortFirstTokenAndStridesKernel` in-server, by trace. The script is `bench/fc_moe/trace_prologue.py`.

| trace (date) | build | W4 verify [56] | W16 verify [176] | draft T=1 [26] |
|---|---|--:|--:|--:|
| g2on / g2full / g2onB (09-05 23:37–23:55) | private copy flashinfer-g2 (A0+A3+G2) | **6.69–6.72** | **6.53–6.59** | 6.85–6.91 (W16), 10.5–11.3 (W4) |
| final0906 (09-06 00:49) | production venv (a0/a3/g2-1/g2-2/g1-pack) | 12.10 | 11.31 | 11.3–12.2 |
| final0906b … wa5prod0221 (to 09-21) | production (+p2) | 11.3–12.5 | 11.3–12.6 | 11.3–12.4 |

What the traces establish:

- **At W16 the whole jump (+4.8 µs at T=16, +5.0 µs at T=1) falls between 09-05 23:55 and 09-06 00:49**:
  - Before: the g2onB build, 6.6 µs.
  - After: production, 11.3 µs.
  - Registers (122) and shared memory (8868 B) are identical.
  - The change in that window: g1-pack was added and the patches were moved from the private copy into the production venv (commits 57d4ef3 and 6b513d2).
- **PDL is not the cause.** The pdl0/pdl1 and pdlh0/pdlh1 pairs give the same prologue time with PDL on and off. In the timeline, the gap to the previous kernel is -0.19 µs.
- **Stream contention does not explain it on its own:**
  - In the G2 build the shared expert's down GEMV also overlaps the prologue, for 3.7 µs.
  - In production the overlap is 6.7 µs (gate_up + down), and then the prologue runs alone for about 5 µs.
- **Contradicting evidence:** the G1b isolated bench (commit 57d4ef3 message) already measured the G2-2 fused prologue at **7.5 / 11.4 µs**, not 6.3 / 6.5.
  - So the "6.6 µs in-server" of the G2 build may be the anomaly.
  - Production's 11.3 µs may simply be this kernel's real cost at T=16.
  - The P2 prune adds histograms and 3 × `__syncthreads`, which accounts for a further 0.3–1 µs (p2-prof2-off 11.55 → p2 12.58 at W16).
- Hence the range **0 .. -5 µs/call**:
  - Per step: W4 49 + 2 calls = **-0.26 ms**; W16/wa 49 + 14 calls = **-0.32 ms**, at most.
  - The fix would not change routing results (same keys, same order), so bit-exact.

**Pending measurement** (§4 command A): prologue time in the microbench for each variant (prod / noprune / nopack / noexpand / all-off), plus with a concurrent side-stream read (side8 / side32).
- If the microbench prod ≈ 11–12 µs, the variants say which piece costs what.
  - A likely suspect is the G2-2 row blocks: every block re-runs the rank, and `__syncthreads` then orders the row load after it (G2_LOG §8 caveat 4).
  - The fix then goes into the private FlashInfer copy (a capped build per the new rules).
- If the microbench prod ≈ 6.7 µs, the in-server environment is stretching it.

  - Next check: delay the shared expert until GEMM1 on the main stream (see §3 note).

## 2. Draft T=1: a route-parallel W4A16 NVFP4 GEMV (target bit-exact)

- **Why it is possible now.** At T=1, 10 routes = 10 distinct experts, so route-parallel reads the same bytes as the CUTLASS grouped GEMM (MOE_SMALLM A7 table: ratio 1.00). N1 has shown that a Triton NVFP4 GEMV reaches 83% of the roof on this card.
- **What it replaces.** About **50 µs** (median):
  - prologue 11.9;
  - GEMM1 17.7 (1040 GB/s effective, 53% of one wave used);
  - doAct 3.5;
  - GEMM2 17.0 (only 540 GB/s).
- **New structure:**
  - k1 (grid I/BN × 10 routes): gate and up for one route, SiLU×mul in registers, written as bf16.
  - k2 (grid H/BN × S route-splits): down projection, with the routing weights and the sum over routes fused in; the fp32 partials are combined by a last-arriver, so it is deterministic.
  - No prologue, no FP4 activation quantisation and no finalize kernel.
  - The top-k ids are read directly.
- **Estimate:**
  - k1 reads 18.4 MB in about 14 µs at 1345 GB/s.
  - k2 reads 9.2 MB in about 7–10 µs. K=640 is short, so efficiency will be lower; I assumed 60%.
  - Total about **23 µs per call, against 50 µs → -27 µs per call**.
  - Per step: W16/wa 14 calls = **-0.38 ms**; W4 2 calls = -0.05 ms.
- **Output.** Only the draft model's numerics change (A16 is used, i.e. more accurate), so the target's greedy output is decided by verification as before. **Acceptance length must be re-measured.** Quantising the activations to FP4 exactly as today would keep the draft close to the current numerics too.
- **Prototype.** `bench/fc_moe/draft_gemv_proto.py`:
  - All 512 experts are resident (1.4 GB, far larger than L2), and each call uses a different set of 10 experts, so it streams from DRAM like the server does.
  - It includes a tile sweep and a check against an fp32 reference.
  - It compiles with `triton.compile` for sm_120 on the CPU. It has **never run on the GPU**.
- **Differences from the server:**
  - The scale factors are the linear layout, while the server's CUTLASS copy uses the 128×4 swizzled layout. The bytes are the same; only the index calculation differs.
  - The gate/up order must be matched to the checkpoint.
- **Effort:**
  - kernel: 2–3 days;
  - draft-side dispatch and CUDA-graph capture: 1–2 days;
  - acceptance A/B: half a day.

## 3. Router GEMV + top-k (rounding-level)

- `_router_triton_kernel` (softmax + top-10) is a separate launch after the router bf16 GEMV [32,10,1].
  - The two sit back to back on the alt stream: W4 4.3 + 4.1 µs, W16 5.2 + 5.3 µs.
  - They are on the critical path; the shared expert on the main stream finishes earlier.
- A last-CTA epilogue in the GEMV would do the top-k: the same counter pattern that w8a16_gemv's split-K already uses.
  - It costs about 1.5 µs in place of about 4 µs → about **-2.5 µs per call**.
  - Per step: W4 51 calls = **-0.13 ms**; W16/wa 63 calls = **-0.16 ms**.
- The softmax sum order changes, so the weights are equal only to rounding. Expert selection works on logits and is unchanged except for exact ties.
- EXCLUSIVE_TIME_MAP shows the router as "100% hidden", but that is exclusive time. On the critical path it is not hidden (the alt stream is the long one).

Note, the contention hypothesis (unmeasured):
- The shared expert's gate_up and down GEMVs (6.3 + 4.2 µs, memory-bound) overlap the first 6.7 µs of the prologue.
- A latency-bound kernel slows down when DRAM queues are long.
- If side8/side32 in §4 A show that the prologue stretches when a side-stream read runs alongside it, the fix is to fork the shared expert after the prologue, so that it overlaps GEMM1 instead. GEMM1's tail wave has idle bandwidth.
- That fix is bit-exact.

### 1b. Session 3 (09:05): what the cold prologue misses

Runs: `runs/fc_moe/gpu3.log` → `s3.jsonl` (`bench/fc_moe/gpu3_cold.sh`). Every cold variant first reads 256 MB on the
same stream, then re-warms one more thing before the measured call (`--touch-inputs`, `--touch-static`,
`--dummy-call`). Median µs, T=1 / T=4:

| before each call | fused prologue (prod) | unfused prologue + expand kernel |
|---|--:|--:|
| nothing (warm) | 7.52 / 8.42 | 6.11 + 4.51 / 7.23 + 4.32 |
| 256 MB read | 11.58 / 12.74 | 6.22 + 4.88 / 7.39 + 4.70 |
| read, then the call's inputs | 10.85 / 12.34 | |
| read, then inputs + the layer's static scales and alphas | 10.88 / 12.35 | 5.92 + 4.29 / 7.04 + 4.22 |
| same, then one T=1 call of the same layer (other routes) | **7.17 / 7.94** | 5.92 + 4.06 / 7.10 + 4.06 |
| read, then only that T=1 call | **7.49 / 8.29** | |
| warm again, end of session | 7.49 / 8.42 | |

- Inputs explain 0.4-0.7 µs of the ~4 µs; the static scales and alphas nothing.
- One earlier call of the same layer removes the whole penalty, even with the inputs left cold.
- The unfused kernels lose only 0.1-0.4 µs when cold, all of it from the inputs. So the penalty belongs to the fused
  kernel itself:
  - **its code:** 105 KB of SASS (k=10, fold). The expand part is unrolled 16 times as straight-line code
    (0x13000-0x19000), while the separate expand kernel is about 15 KB and loops;
  - **or per-call state it shares with the earlier call:** the workspace, allocated per call from the same graph-pool
    block, and its TLB entries.
  - Its kernel parameters are unlikely: the earlier call has its own graph nodes.
- In the server the fast mode is the same thing: the previous layer's MoE call ran this kernel, and the weight streaming
  between the two calls decides whether its lines survive in L2.
- **Switching production to `FLASHINFER_MOE_FOLD_EXPAND=0` does not pay.** Whole chain, cold (inputs + static
  re-warmed): fused 47.73 / 66.98 µs, unfused 46.50 / 65.17 (-1.2 / -1.8). Warm: fused 43.34 / 59.71, unfused
  45.54 / 61.41 (+2.2 / +1.7). With 44-70% slow calls at W4 that nets about zero, and at T=16 (all cold) unfused is
  1.5 µs worse (§4b.2).
- Next split (session 4, `bench/fc_moe/gpu4_k8.sh`): an earlier call with top-k 8 runs another instantiation (other
  code) but shares the workspace pool, the static data and the module's code pages. Fast means workspace or TLB; slow
  means the k=10 kernel's own instruction lines.

### 1c. Session 4 (09:41): the penalty is the k=10 kernel's own instruction lines

Runs: `runs/fc_moe/gpu4.log` → `s4.jsonl` (`bench/fc_moe/gpu4_k8.sh`). Every cold variant reads 256 MB, then the
call's inputs and the layer's static data, then makes one T=1 dummy call that shares one thing with the measured call.
Prologue median µs:

| dummy call before the measured one | what it shares with the measured call | T=1 | T=4 |
|---|---|--:|--:|
| no read at all (warm) | everything | 7.52 | 8.42 |
| none | - | 11.01 | 12.48 |
| same kernel (top-k 10), same layer | code, workspace pool, static data | 7.20 | 7.94 |
| same kernel, own 64 MB workspace | code, static data | 7.20 | 7.94 |
| same kernel, layer 5 | code, workspace pool | 7.20 | 7.95 |
| top-k 8 instantiation | workspace pool, static data | 10.66 | 12.35 |
| top-k 4 instantiation | workspace pool, static data | 9.82 (p90 11.67) | 12.38 |

- Only a run of the same instantiation removes the penalty. The workspace, its TLB entries and the layer's data do
  not matter.
- The kernel reads no constant-bank literals: every `c[..]` reference in its SASS is bank 0, the launch's own
  parameters. So what the earlier run leaves in L2 is the kernel's instruction lines.
- Why only the fused kernel pays: its expand path is ~20 KB of straight-line SASS (the quantize loop unrolled 16
  times; 10 trips run at hidden 2560). Code without memory stalls runs only as fast as its instruction lines arrive,
  so after a flush every line costs a DRAM round trip.

- The top-k 4 dummy's partial gain at T=1 (wide p10-p90) hints at shared non-inlined callees. The fix does not need it.

**Fix RQ1:** roll the quantize loop (`#pragma unroll 1`). The loads stay unrolled, so the whole row is still in flight
at once; `staged[]` moves to local memory (L1).
- Bit-exact by construction: the per-chunk arithmetic is unchanged.
- Expected: most of the 3.5-4.5 µs cold penalty goes, and warm calls get 0.1-0.3 µs slower.
- Built in the private copy `~/tools/flashinfer-p2` (09:51-09:57, the instantiation TU and the link; capped scope).
