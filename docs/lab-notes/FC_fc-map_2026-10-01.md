## 0. Conclusions (read this first)

1. **The fixed part of a step is about 7.2 ms, and about 3.2 ms of it is above the physical floor.** Fit on the x20152 traces (S = 3 and 15, code + prose): intercept 7.21 ms, floor 4.04 ms.
   - Most of the 3.2 ms sits in areas the other owners already cover:
     - MoE prologue and GEMM wave quantization: 1.13 ms → fc-moe
     - HC chain: 0.78 ms → fc-glue #2; the MEGAKERNEL data caps what is realistic
     - attention/QSA: 0.35 ms → fc-glue #3
   - What is left for new work: shared expert + router 0.25 ms, GDN core 0.17 ms, draft_extend 0.16 ms, and small GEMV tails of about 0.1 ms each.
2. **Almost nothing is lost outside kernels.**
   - The CPU is 6.3–8.2 ms ahead of the GPU in steady state, so scheduler, adaptive draft-length control and output processing are fully hidden.
   - No CPU–GPU sync sits on the critical path.
   - GPU idle time is 75–83 µs/step at W4 (0.9%) and 128–144 µs at W16. Of this, 10.5 µs at W4 is one GPU-side bubble at the start of the draft graph. The rest is the ~0.1 µs gaps between kernels inside graphs.
3. **Sampling adds +0.25..0.30 ms/step, measured on 10-01 (§5b)**: W4 +0.25..0.27, W16 +0.30, wa +0.26..0.28. That is 2–3× the code estimate below (+0.08..0.16 at W4, +0.12..0.22 at W16/wa). In this build the top-p step runs as FlashInfer's AIR top-p (two kernels, 120–139 µs/step), not the one-CTA-per-row kernel described next.
   - The whole sampling verify runs **eagerly, outside the CUDA graphs**.
   - It does full-vocabulary work (248,320 entries per row) five times: divide by temperature, softmax, top-k renorm, top-p renorm, and a `zeros_like` of the same size.
   - The expensive part is FlashInfer `top_p_renorm_probs`. It uses **one CTA per row** and makes **4–12 full-row passes**: a CPU replay of the kernel's search loop on top-k-40 rows needs 2–10 search rounds, with a median of 6–8 (`prof/fc_topp_rounds_sim.py`).
   - A sparse top-k path (§3.3 F2) would remove most of this cost. The change is at rounding level.
4. **Correctness finding (changes output; commander, please look):** `min_p` is **ignored** in speculative verify.
   - `eagle_sample` never reads `need_min_p_sampling`.
   - LM Studio's `min_p=0.05` therefore has no effect on any token while spec decoding is on: neither on the accepted draft tokens nor on the bonus token.

## 1. Task 1: intercept by block

### 1.1 Method

- Tool: `prof/fc_map.py`. The step window is measured on the GPU clock, from the first kernel launched by the `draft` annotation of step i to the same point of step i+1. The CPU runs at least one step ahead, so CPU annotations are not step boundaries.
- Attribution: every µs of the window belongs to the **oldest running kernel**. With PDL, a waiting kernel is resident early and spins, so a fair split would charge the producer's time to the waiter. For example, `_fused_sigmoid_mul` looks like 16.8 µs under a fair split. fc-glue found the same effect independently.
- Fit: `t_block(S) = a + b·S` by least squares.
- Floors, as the larger of two values per block (not added):
  - weight bytes streamed once per step ÷ 1.6 TB/s;
  - 0.67 µs per launch in the chain (MEGAKERNEL §3.2).

  The MoE floor assumes T = 1 with 10 experts.
- Run: `fc_map.py prof/traces/x20152-w4-code-edit:3 …-w4-prose-en:3 …-w16-code-edit:15 …-w16-prose-en:15`.

### 3.2 Correctness observations (these change output; put them in the quality track)

1. **min_p is dropped.**
   - `SamplingBatchInfo.need_min_p_sampling` (sampling_batch_info.py:205–209) is never read in `eagle_sample`.
   - The draft graph also hard-codes `need_min_p_sampling=False` (`eagle_draft_cuda_graph_runner.py:409–414`). That one is harmless because the draft is argmax.
   - Result: with spec decoding on, tokens below `0.05 × p_max` can be sampled, which LM Studio's settings exclude.
   - Fix: after top-p, zero out entries `< min_p · max(prob)` and renormalise, in the same order as the non-spec sampler (top-k → top-p → min-p).
2. **Target-only mode and rejection sampling behave differently.**
   - `tree_speculative_sampling_target_only` gets `draft_probs = 0`. It accepts draft token x with probability p_target(x) and samples the bonus token from p_target.
   - The commander's `--speculative-use-rejection-sampling` (chain Triton) needs a full-vocabulary `draft_probs` of shape T × V.
   - With the hot-vocab draft (49,152 entries), this means one more T × V fp32 buffer per step: a scatter from 49,152 to 248,320, then a read by the accept kernel. That costs an estimated +10..25 µs/step on top of §3.1, plus a draft softmax per draft step. Keep the draft softmax inside the draft graph.

### 3.3 Fix proposals for the commander (I did not modify the fork)

- **F1 (S2; bit-exact, trivial):** at 812–816, replace `torch.zeros_like(target_probs)` with one persistent zero buffer, kept per (bs, T, V) and allocated outside `borrow_graph_pool`. The kernel only reads it. Saves 3–10 µs.
- **F2 (S1; rounding-level; main item):** a sparse top-k verify, following `dflash_utils.py` ~1007–1070 (`build_dflash_verify_target_probs` already does this). Steps:
  1. `vals, idx = torch.topk(next_token_logits, k=max_top_k)` on the raw logits. Dividing by a temperature > 0 does not change the order, so divide only the 40 values afterwards.
  2. softmax over the 40 values
  3. top-p on the sorted cumulative sum
  4. min-p mask (fixes §3.2-1 for free)
  5. renormalise
  6. Either:
     - (a) scatter into a persistent zero T × V buffer and clear the 40 × T positions from the previous step, which keeps the existing sampling kernels unchanged; or
     - (b) accept/reject directly on the sparse form. Chain topk = 1 needs only p(x_draft) and a 40-way bonus sample.

  All full-vocabulary passes except one top-k are removed. The remaining work is one multi-CTA top-k plus about 10 tiny kernels, roughly 20–40 µs.

  Net saving: -0.05..-0.13 ms at W4 and -0.08..-0.18 ms at W16/wa.

  Output difference: the full softmax followed by top-k renorm equals the 40-way softmax mathematically, but fp32 rounding differs. When several logits tie at the k-th value, a different one may be kept.

  For rejection sampling, the residual `max(0, p_t − p_d)` needs only the union of the two supports: 40 entries plus the draft's top entries, or at worst 49,152 hot-vocab entries. That is still 5× less than V.
- **F3 (not recommended):** capturing the sampling path into the verify graph. The CPU is already 6 ms ahead, so this hides launches that are already hidden: ≈0 gain.
- The FlashInfer sampling JIT module is cached (`~/.cache/flashinfer/0.6.17/120f/cached_ops/sampling/sampling.so`, 09-18; no FlashInfer source is newer), so the first sampling request should not trigger a compile.
