# FC fc-glue (2026-10-01): latency-bound small kernels and clocks

Sub-task fc-glue (port 8013). Scope: which part of the fixed cost per step
(`7.943 + 0.5554·S ms`) in bs=1 decode comes from latency-bound small kernels and the GPU clock,
and how much of it can still be cut.

Unless stated otherwise, all numbers come from existing 09-07/09-10 chrome traces, analysed on the CPU:
- `prof/traces/x20152-w4-code-edit`
- `prof/traces/x20152-w16-code-edit`
- `prof/traces/x3wa2336-wa-{code-edit,prose-en}`

GPU measurements (microbench, bandwidth probe) did not run: the lock was busy before the crash, and after the 03:00 reboot a driver upgrade left the GPU hanging. They are listed with their commands under "Pending" (§4). **GPU time used: 0 min.**

Ideas 1 and 2 are the only ones cheap enough to try immediately, and both are bit-exact.

Important finding: the 09-07 exclusive map undercounts time.
1. With PDL, the next kernel starts early and spins in `griddepcontrol.wait`.
2. The sweep line counted that spin as "shared", so the producer kernel's exclusive time looked too small.
3. After clipping each kernel's start to the end of the previous kernel on the same stream (`bench/fc_glue/excl_pdl.py`), W4 changes as follows:
   - shared 1709 → 1344 µs, exclusive 6887 → 7252 µs;
   - verify `kernel_mha` goes from 8 µs to **182 µs**.

"PDL hides attention" is therefore an accounting artifact: every attention call puts 16-19 µs on the critical path.

### 1.4 Idea 1: dispatch starvation of `in_proj_ba`

- **Code path:** `qwen3_5.py _forward_input_proj_direct`. It launches qkvz on the main stream first, then ba on the alt stream. The comment says "b/a first", but the order is the opposite.
- **What goes wrong:** qkvz has 512 (W4) / 256 (W16) CTAs. ba's 3 CTAs cannot get an SM until qkvz's CTAs drain, so ba starts about 26 µs late and sticks out 1.7-3.4 µs past qkvz.
- **Cost:** the exposed part is 93-94 µs/step at W4/W16 and 115-186 µs at wa. It is paid once per GDN layer in each verify forward (36 calls per step, independent of S).
- **Fixes, all bit-exact** (same kernels, same inputs, only the order changes):
  - (a) Swap streams: ba on main (its PDL launch is dispatched first), qkvz on alt. This loses PDL for qkvz (about 0.15 µs × 36).
  - (b) Grid merge: add a `pid < 3` branch inside the qkvz kernel that computes ba.
  - (c) Raising the alt stream's priority. Likely ineffective, because qkvz is a single wave.
- **Expected gain:** 50-100% of the exposed time. The microbench `bench/fc_glue/bench_gdn_front.py` measures it with the real kernels under CUDA-graph replay:
  - variants: `prod`, `swap`, `gside`, `gside_swap`, `serial`, and the lower bounds `no_ba` and `bare`;
  - it also dumps the per-stream timeline.
  - Not run yet (see Pending).

### 1.5 Idea 2: move `hc_combine_gate` to a side branch

- **Inputs:** the gate only needs K0's normed output and `inject_weight` [4,10240].
- **Today:** it runs alone (1.5 µs plus the launch gap) between K2 and qkvz.
- **Change:** fork it onto a side stream right after K0 so it overlaps K1/K2. K1 uses 100 CTAs and K2 160, so SMs are free.
- **Consumer:** `hc_combine_apply`, fused into the next layer's K0 (R7/H2), so joining at the end of the layer is enough.
- **Upper bound:** the gate's exclusive time, W4 118 / W16 156 / wa 141-251 µs.
- **Risks:**
  - Bandwidth contention: K1/K2 read fp8 weights of 3.3 MB/layer, and the gate reads inject 80 KB, so contention is likely small. There is a precedent of contention in L2_PREFETCH.
  - Adding a fork/join inside a graph costs about 1 µs per event edge.
- **Implementation:** `hyperconnection.py _early_gate` and `hc_mix2_triton.hc_norm_mix2` need a hook between K0 and K1. The microbench does this with `_DownProxy`. Measured by the same microbench (Pending).

### 1.6 Idea 3: decode attention with a small fixed cost

- **Why:** XQA `kernel_mha` (sm120 has no trtllm-gen kernel) costs 16-19 µs per call in the server and about 10 µs even in the J2 bench, and that time does not depend on KV length (J2). QSA looks at 2048 tokens × 2 KV heads × 256 dims in fp8, i.e. 1-2 MB per layer, which is ≈1 µs at roofline.
- **Target:** a split-KV kernel with ≤5 µs fixed cost, 1 CTA per head group, reduction in shared memory. Estimates:
  - verify: 12 layers × (16→6 µs) ≈ -0.12 ms;
  - draft: S × (16.7→5 µs), which is -0.02 (W4) / -0.16 (W16) ms.
- **Output impact:** only the fp32 summation order changes, so differences stay at rounding level. The target's greedy output could flip a token in rare cases, so an N1/DH-style match-rate check is needed.
- **Effort:** high. It is a new kernel (FA2-style decode, QSA page table, fp8 KV).

### 1.7 Idea 4: draft MoE path (one draft forward)

- **Measured draft forward (W16):** 266 µs.
  - lm_head 81.8; tail 15.9; MTP fc 14.8; HC mix 11.9 + 12.3 + 11.3; in_proj 23.1; rope/kv/meta 8.8; mha 18.2; o_proj 12.2; MoE routing ~20; GEMM1 + act + GEMM2 37.7.
  - Weights ≈236 MB, which is ≈147 µs at roofline, so about 120 µs per forward is not weight streaming (×14 ≈ 1.7 ms/step at W16).
- **Target:** the MoE critical path (router → topk → prologue 12 → GEMM1 17.5 → act 3.3 → GEMM2 16.1 ≈ 57.6 µs) could shrink to about 25 µs with a single-CTA-routing + fused NVFP4 GEMV for M=1 (MOE_SMALLM A7: at T=1 the extra traffic factor is 1.0).
- **Gain:** -30 µs per forward: W16 -0.42 ms, W4 -0.06 ms.
- **Output impact:**
  - Verification is greedy, so draft numerics change only acceptance length.
  - The parent is currently testing rejection sampling (`--speculative-use-rejection-sampling`). With it the output distribution stays exact, but individual samples change.
- **Effort:** high.

### What sets the SM clock ceiling

- No event reason is active while the clock sits at 2300 MHz, so this is the top of the default boost curve (voltage/reliability limit, which nvidia-smi does not show). It varies by about ±100 MHz with temperature bins.
- The 3090 MHz is reachable only with a clock offset (overclock).
- `-lgc` cannot go above the curve. At best it stops the drops caused by temperature bins, worth ≤1%.
- **Power is not the limit during decode.** It could be during prefill or with the 300 W limit, but that was not checked.

### How much of a step scales with the SM clock (estimated)

- W4 (8.8 ms):
  - DRAM-bound large kernels (MoE GEMM1/2, GEMVs, lm_head) ≈4.5 ms, which does not scale;
  - HC up/down ≈0.86 ms, mixed;
  - latency-bound kernels + launch/PDL gaps ≈2.9-3.4 ms, which scales with 1/f_SM.
  - So **about 35-40% of the W4 step scales with SM clock**. W16/wa: about 30-35%.
- A hypothetical +10% SM clock (overclock) → -3..-4% step time.
  - **Not recommended:** ECC is off, so a compute error from marginal voltage would pass silently. It needs an overclock-offset tool, which nvidia-smi does not provide.

### User-only knob with a real chance (U1): memory clock

- The DRAM-bound part is about 4.5 ms at W4 and ≈8.5 ms at W16. With a 4.8% higher memory clock, the upper bound is **W4 -0.2 ms (-2.3%), W16/wa -0.4 ms (-2.5%)**.
- 14001 MHz is the board's standard P0 rate, not an overclock.
- **Commands, for the user only:**
  - `sudo nvidia-smi -cc 1` (CUDA clocks override: stop CUDA from dropping the memory clock), or `sudo nvidia-smi -lmc 14001`.
  - Undo with `-cc 0` / `-rmc`.
- **Risks:**
  - With ECC off, memory errors would go undetected. It is the same rate used for graphics, so the risk is small, but after the change check that the N1-style greedy outputs match production exactly.
  - Power goes up by a few W, so combined with the 300 W limit, SW power capping could engage in prefill.
- **Before asking the user:** run `bench/fc_glue/bw_probe.py` (Pending) to measure whether DRAM bandwidth actually moves between 14001 and 13365.

**Proposed user experiment to measure SM-clock sensitivity** (safe, because it only lowers the clock): profile one W4 step at `sudo nvidia-smi -lgc 1800,1800` and again at default (`-rgc`), then compare per-family medians. The families that get 1.28× slower are the latency-bound ones.

## 3. Places that are not cuttable (checked)

- Deleting K0 (J1), merging K1 and K2, and folding the gate into K0 (HC_GATE_EARLY=1): all measured as worse.
- Barrier-style fusion and megakernels (MEGAKERNEL_SPEC): the barrier costs more than PDL.
- XQA split and grid tuning (J2): already optimal; the fixed cost is inside the kernel.
- Split-K for in_proj_ba: slower in the server.
- Raising the SM clock with a clock lock: not possible (it is already at the top of the curve and nothing is limiting it).
- The "PDL hides attention" claim in the 09-07 map is an accounting artifact, so there is no free attention time to count on.
